# Shared Backend Contract

Updated: 2026-08-12

This document defines project-level contract rules shared by the customer app and POS/Admin dashboard. It is not a complete schema specification.

## Contract ownership

- Trusted authority: shared Supabase/backend.
- Canonical migrations: `Hermann-33/Aida_System/supabase/` until superseded by ADR.
- Customer and dashboard adapters consume one contract.
- UI fixture/model shapes do not dictate database tables.

## Identity and membership contract

Current stable backend concepts:

- Supabase Auth user ID is customer authentication identity.
- `user_profiles` stores trusted application role plus basic profile data.
- Public customer signup always provisions `app_role=customer`; signup metadata cannot grant staff/admin/owner.
- `members` stores a server-issued stable `member_code` generated by the backend.
- Signup accepts `display_name` and `is_student` only as untrusted declarations.
- Standard declaration -> `member_type=standard`, `student_status=not_submitted`.
- Student declaration -> `member_type=student`, `student_status=pending`.
- `verified`, `rejected` and `expired` student outcomes require trusted review workflow; frontend metadata is never authority.
- Customers read their own profile/member under RLS.
- Bulk member/profile listing is admin/owner only. Ordinary POS staff must use a later bounded member-lookup capability rather than a bulk customer directory.
- `public.list_admin_members()` is authenticated-only, explicitly checks admin/owner and runs `SECURITY INVOKER` so forced RLS remains active.
- QR/member code is lookup material, not authentication.

## Dashboard member-directory transport

The browser contract is same-origin `GET /api/v1/admin/members` using the existing employee/admin HttpOnly session direction. The server/BFF must:

1. authenticate the employee/admin session;
2. reject disabled/unauthorized/non-admin callers;
3. execute the trusted admin member-directory capability as an authenticated role;
4. return only required member-directory fields;
5. never expose service-role/database secrets to the browser.

Until that server runtime exists, the dashboard member path is `PARTIAL` even though the database capability and browser adapter exist.

## Money and pricing

Store/transport money as integer minor units (sen) unless superseded by ADR. Clients submit IDs/quantities, not trusted prices/totals. Trusted quote/order logic validates publication, availability, modifiers, discounts and final totals. Receipt snapshots preserve historical purchased descriptions/prices.

## Staff/branch authorization

Staff/admin authorization comes from trusted employee/application-role records, never hidden UI, client storage or editable Auth metadata. Branch scope, manager approval, terminal credentials and revocation are server checked and audited.

## Orders/payments/loyalty/inventory

- Orders require explicit legal states, idempotent creation and trusted transitions.
- Raw payment credentials never enter ordinary app/database fields; approved provider/device boundaries own sensitive handling.
- Loyalty/voucher balances and consumption derive from auditable server-side events and atomic operations.
- Inventory requires trusted units/location scope and auditable movements.

## Time, concurrency, realtime and cache

Business time/expiry decisions use server time. Replay-sensitive operations require idempotency. Balance/stock/order transitions are atomic or serialized. Realtime follows the same RLS/role/branch scope as ordinary reads. Cached/offline values never authorize stale price, role, loyalty or order mutations.

## Contract change gate

A breaking shared contract change remains `PARTIAL` until migration/API/RPC behavior, security/RLS tests, both client adapters and mirrored documentation are all verified.
